# 自作アプリ共通デバッグ標準 v1

この文書は、ChatGPT/Codexを含む開発作業で「動いたように見える」ではなく、再現可能な根拠を持って品質確認するための共通ルールです。

## 1. 基本原則

- 仕様書・README・既存の決定事項を先に読み、仕様を推測で変更しない。
- バグ修正は、可能な限り「再現テストを追加 → 修正 → 再テスト」の順で行う。
- 既存の正常動作を壊していないことを回帰テストで確認する。
- テストできなかった項目は「未確認」として明示し、完了扱いにしない。
- 外部API・位置情報・端末依存機能は、成功時だけでなく拒否・失敗・タイムアウトも確認する。
- ユーザーの入力や操作順を信用しすぎない。誤操作・連打・空欄・戻る・再読み込みを試す。
- 画面上の見た目だけでなく、保存状態・履歴・確率・候補集合・API送信内容も確認する。
- 実装やテストがないことだけを根拠に、仕様上の動作を推測しない。仕様外の挙動は記録し、勝手に追加しない。

## 2. 毎回確認するテスト分類

### A. 正常系

主要な利用フローが仕様どおり最後まで完了する。

### B. 異常系

空入力、取得失敗、不正レスポンス、保存失敗、ネットワーク失敗などで壊れない。

### C. 境界値

0件、1件、2件、多数、最小値、最大値、端数、同値などを確認する。

### D. 状態遷移

入力後の条件変更、戻る、画面切替、再実行、履歴復元、保存後の再利用を確認する。

### E. 誤操作・連続操作

二重クリック、連打、素早い画面移動、同じ項目の追加削除、途中キャンセルを確認する。

### F. 永続化

localStorage、DB、履歴、保存済みデータが、再読み込み後も仕様どおり扱われる。

### G. 外部依存

API、位置情報、地図、認証などについて、成功・拒否・失敗・タイムアウト・空結果を確認する。

### H. UI/端末

主要スマホ幅、PC幅、長文、スクロール、キーボード表示、アクセシビリティの基本を確認する。

## 3. 自動テストの優先順位

1. ドメイン/計算ロジックのユニットテスト
2. 主要ユーザーフローの統合テスト
3. バグ再発防止テスト
4. API境界のテスト
5. 必要に応じてブラウザE2E

テスト数を増やすこと自体を目的にしない。壊れたら困る仕様と、過去に壊れた箇所を優先する。

## 4. シナリオベースの意地悪テスト

各アプリで、最低でも次を検討する。

- 何も入力しない
- 1件だけ
- 2件だけ
- 非常に多い件数
- 同じ操作を連打
- 操作途中で条件変更
- 結果表示直後に別画面へ移動
- 戻る/再読み込み
- 保存後に再起動
- 保存データが欠損または古い形式
- APIが0件
- APIが4xx/5xx
- APIが遅い
- 通信途中で失敗
- 外部機能の権限拒否
- 画面幅が狭い
- 長い文字列
- 日本語以外・記号・絵文字を含む入力

アプリにない外部依存機能は対象外とし、その理由をアプリ固有マトリクスに記録する。

## 5. バグ発見時の記録

最低限、次を残す。

- 概要
- 重要度: Critical / High / Medium / Low
- 再現手順
- 期待結果
- 実際の結果
- 原因
- 修正内容
- 追加した再発防止テスト
- 再確認結果
- 未確認事項

## 6. 修正ループ

1. 再現する
2. 可能なら失敗する自動テストを追加する
3. 原因を特定する
4. 最小限の修正を行う
5. 対象テストを実行する
6. 全体テストを実行する
7. buildを実行する
8. 必要なら実機/ブラウザ確認を行う
9. 結果を記録する

同じ不具合に対して、原因不明のまま場当たり的な修正を重ねない。

## 7. 完了条件

原則として以下を満たしたときのみ「デバッグ完了」とする。

- 主要フローの自動テストがPASS
- 回帰テストがPASS
- production buildが成功
- Critical / High の既知バグが0件
- Medium / Low の既知バグは記録済み
- 主要端末/画面幅で致命的なUI崩れがない
- 外部依存の失敗時挙動を確認
- 未確認事項を明記

## 8. ChatGPT/Codexへの標準指示

デバッグを依頼された場合は、次の順で進める。

1. 仕様と既存テストを読む。
2. この標準とアプリ固有のテストマトリクスから不足ケースを洗い出す。
3. まず現状のテスト/buildを実行する。
4. 再現可能なバグはテスト化してから修正する。
5. 修正後、対象テスト → 全体テスト → build の順で再確認する。
6. 最後に「PASS / 修正済み / 未確認 / 外部依存」を分けて報告する。

## settlement-appへの適用

- 金額計算では、円単位の整数、端数配分、受取/支払総額、送金先、ゼロサムを具体的な値で確認する。
- 通常精算は明細ごとの対象者変更を区間負担として検証する。
- 保存はlocalStorageとJSONバックアップの正常・不正・失敗経路を確認する。API/DB/Sheetsがない場合はN/Aとする。
- UIは320/375/390pxとPC幅を確認する。実機キーボードを使っていない場合は未確認とする。
- settlement-app固有のケースと証拠は `docs/DEBUG_MATRIX.md`、実行結果と残件は `docs/STATUS.md` に記録する。
