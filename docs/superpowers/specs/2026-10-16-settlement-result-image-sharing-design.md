# 最終精算結果の画像共有 設計

## 目的と合意した範囲

記録を入力した人が、確定した最終収支を参加者へ一度に伝えられるようにする。共有するのは全員分を載せた1枚のPNG画像とし、情報を省略せず、見出しと余白で読みやすくする。対象は通常精算・ポーカー・麻雀・ノリ打ちの4モード。ルーレット、元の支払い明細、半荘ごとの記録は対象外とする。

既存のブラウザ内保存を維持する。共有画像は端末内で準備し、利用者が操作したときだけ共有先へ渡す。アプリ独自のサーバーや公開URLには送らない。画像を受け取った人が記録を編集する機能は設けない。

## 画像に載せる情報

- 記録名、モード名、画像を生成した日時。
- 参加者の表示順で、全員の名前と最終収支。プラスは「受け取り」、マイナスは「支払い」、ゼロは「0円」と明示する。
- 確定した送金指示を全件。「誰から・誰へ・何円」を1件ずつ記す。送金が不要な確定結果は「送金なし」と記す。
- 収支が一致していることを簡潔に示す。画像だけで意味が通るよう、金額の単位は円と明示する。

明細、半荘、入力フォーム、保存状態、操作ボタン、アバターは画像に含めない。人数や名前が増えても、全員・全送金を省略せず、画像の高さと折り返しを調整する。結果画面の表示と画像は同じ確定済みの計算結果を使い、別の計算式を持たない。

## 画面と利用フロー

対象4モードの結果カードに「画像を共有」と「PNGを保存」を置く。ボタンは現在開いている記録だけを対象にする。参加者が0人、入力途中に無効な値がある、計算結果に問題や差額がある場合は確定結果として出力できない。利用者には、その理由を結果カード上で確認できるようにする。収支が有効で全員0円の場合は出力でき、「送金なし」を表示する。

「画像を共有」は、PNGファイルを渡せる端末・ブラウザではOSの共有メニューを開く。共有先の選択と送信は利用者が行う。画像ファイルの共有に対応しない場合は、同じPNGを保存できる案内を出す。「PNGを保存」は対応環境に関係なく常に用意する。共有のキャンセルはエラー扱いにせず、生成・共有の失敗では元の記録を変更しない。

## 構成と採用理由

候補は (1) 表示中のDOMを撮影、(2) 結果データから共有専用画像を描画、(3) 利用者にOSスクリーンショットを任せる、の3つ。採用するのは (2)。画面幅やスクロール位置に依存せず、不要な操作UIを除き、長い名前・人数に合わせて高さを決められるため。画像描画は既存の `SettlementResult`、参加者、記録名、モード、出力日時を受け取り、PNGを作る専用モジュールに分離する。日本語を描ける端末標準フォントを使い、外部画像・リモートフォントへの依存を避ける。

共有処理は画像描画とは分ける。`navigator.canShare({ files })` でファイル共有可否を判定し、可能なら利用者のクリックから `navigator.share()` を呼ぶ。共有APIに必要な利用者操作を失わないよう、画像ファイルは有効な結果の更新後に準備し、現在の記録・結果と一致するファイルだけを共有可能にする。生成中はボタンの状態を示す。PNG保存では同じファイルを使う。画像が作れない場合は理由を表示し、切れた画像や古い結果を共有しない。

`ResultPanel` は結果表示と共有操作の入口を持つ。各モードは現在の記録情報と、画面に表示している確定結果を渡す。ルーレット画面は変更しない。共有は保存形式や計算式を変えない。

## 検証条件

- 4モードそれぞれで、画像の参加者別収支・送金指示が画面の確定結果と一致する。
- 送金0件でも「送金なし」の画像ができる。参加者0人、無効入力、収支不一致では出力できない。
- 長い日本語名、複数参加者、多件数の送金、正負・ゼロの金額で欠落・文字切れがない。
- 共有API対応時はPNGを渡し、非対応時・共有キャンセル時・生成失敗時の表示と記録不変を確認する。
- スマホ幅とPC幅でボタンと結果カードを確認し、`npm test`、`npm run typecheck`、`npm run build` を通す。

## この設計で扱わないこと

共有URL、クラウド同期、アカウント、共同編集、実際の送金処理、PDF、テキスト共有、ルーレット結果の共有は今回追加しない。
